Repository page · redesign proposal

Agents first

The repository page carries seven concerns in one column and hides half behind an accordion that mixes settings with analysis. Worse, it leads with generic delivery metrics — as though this were a DORA dashboard. It is a tool for improving coding agents, so the first thing you see should be how the agents are doing, and the delivery numbers should be sliced by which agent did the work.

The diagnosis

Four jobs, one scroll

Everything currently on /repos/[repoId], grouped by what a reader is actually trying to do. The problem is not the amount of information — it is that four different intentions are interleaved, so no section has an obvious home.

Inside “Advanced gate analysis” — an accordion that also holds analysis

The accordion is the tell. “Advanced gate analysis” contains a configuration form, an import control, two data tables and a set of metric cards. A label that has to cover configuration and analysis at once is a label covering for a missing structure. In the redesign it does not get renamed — it disappears, because every one of its children has a real home.

The proposal

Agents lead. Delivery supports. Configuration gets out of the way.

Click the tabs — Agents and Delivery are mocked in full, Settings too. The header and tab bar persist across all five, because repository identity and evidence coverage are true regardless of which view you are in.

Four decisions worth arguing about

  • The cohort table is the product. “Copilot pull requests take twice as many attempts to go green as Codex ones” is the sentence this tool exists to produce, and nothing on the page says it today. Your own docs/future.md already called for it: compare first-pass rate and attempts-to-green by provider while preserving an explicit unknown cohort. The unattributed rows stay their own cohort and are never folded into a total.
  • The rarity card is the hero, and it needed a flavour line. A trading card puts the species line under the name and the attack under that — the finish tells you how rare it is, the text tells you what it does. Silver · Holographic on its own is decoration. Saying what Silver means, then listing the two moves that reach Gold and what each is worth, makes it information — and gives the card the height it needed to sit level with the column beside it.
  • Readiness and involvement stay separate. Readiness asks whether the repository is a place an agent can work; involvement asks which agents actually do. A repository can score 96 and have no agent ever touch it — that gap is worth seeing, not averaging into one number.
  • The coverage strip sits above every number it qualifies. This product’s claim is that missing evidence stays unknown rather than guessed. That claim currently lives in six definition rows halfway down the page, below the figures it applies to.
  • The date range belongs to Agents and Delivery, not the page. Today it sits in the header, implying it filters the PR table and the gate policy. It does not.

The copy

What each finish means

Six tiers already exist in gradePresentation() with labels, colours and symbol counts. None of them has a sentence. These are the sentences — one flavour line per tier, written from the agent's point of view rather than the grader's.

ScoreFinishFlavour line
0–49
Bad		Common · Flat An agent will guess. There is no reliable way to build this, test it, or find the thing it needs to change.
50–69
Mediocre		Shimmer · Light holo An agent can start, but will stop to ask questions a document should already answer.
70–79
Good		Bronze · Holographic Enough context to work from. Verifying the change still takes trial and error.
80–89
Very good		Silver · Holographic Readable, testable, navigable. An agent can find its way around and verify its own work without asking a human first.
90–99
Excellent		Gold · Holographic An agent can land a change unaided. Documentation and verification both hold under pressure.
100
Excellent		Prismatic · Perfect Nothing the rubric asks for is missing. Rare by construction — reserved for exactly 100.

The Next tier block is generated, not written: the rubric already returns per-check points and a pass or fail, so the failing checks sorted by points are the moves, and the distance to the next threshold is arithmetic. At Prismatic the block is replaced by a single line, because there is no next tier.

What this costs to build

Next.js nested layouts give you the persistent header and tab bar for free. One new layout owns the header; each tab is a page beneath it. Two of the five already exist and move unchanged.

The two new pages are mostly moved markup — the gate form, failure table and PR table already exist and keep their server actions.

The cohort table is the one genuinely new thing, and it is closer than it looks. The branch just merged stores agent_markers and head_ref on every pull request, and detectExecuted already derives which pull-request ids belong to each agent — it just aggregates them away. What is missing is the per-pull-request projection: writing that agent set back onto the PR, which is the agent_provider column that has sat unused since the first migration. Then the existing metric aggregation groups by it. That is slice four, and this design is the argument for building it.
